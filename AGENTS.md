`packages/typed-css-modules-mapper` is the published content mapper. `src/transform.ts` turns CSS into the virtual TypeScript module and its span mappings, `src/server.ts` speaks the content mapper protocol over stdio, and `src/protocol.ts` types that protocol. `e2e/` runs the built mapper through real `tsc` (TypeScript 7.1) and `tsrs` binaries, and the `tsc` language server; `examples/vite` shows the runtime side.
Every behaviour must hold for both compilers. When you add a fixture to `e2e/fixtures`, add its expected output to `e2e/compile.test.ts`; both compilers are checked against the same string. Fixtures are excluded from oxfmt and oxlint because the expected diagnostics depend on their exact positions.
The package README is the user documentation and is what npm shows; the root README repeats it (everything before `## License`) for GitHub, and a test fails when they drift. A user-facing change is not finished until both cover it. Write it for someone using the mapper: what to configure, and what they will observe.
When making changes that affect the published package, create a changeset (.changeset/<name>.md). Use patch/minor/major as appropriate. Normally use one direct sentence stating the user-visible outcome. A changeset becomes a CHANGELOG entry, not a miniature PR description: never narrate the implementation, investigation, tests, edge cases, rationale, or review history.
Before committing, always run `pnpm run verify`. It builds, checks formatting and lint, typechecks, then runs the unit and e2e tests. Use `pnpm format` and `pnpm lint` to fix what it reports.
When creating a pull request, always follow .github/PULL_REQUEST_TEMPLATE.md and fill any non-applicable sections with N/A.
